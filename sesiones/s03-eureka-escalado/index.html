    S3 - Registro, descubrimiento y ejecución concurrente de servicios

    1. Introducción

    Tiempo: 20 min.

    1.1 Propósito

    Incorporar registro y descubrimiento de servicios para que los microservicios puedan encontrarse por nombre lógico y ejecutarse en múltiples instancias.

    1.2 Resultado de aprendizaje

    El estudiante implementa un servidor de descubrimiento, registra microservicios con puertos dinámicos y verifica múltiples instancias activas.

    1.3 Producto de sesión

    Registry Server (Eureka) operativo en infra/registry-server, con los seis microservicios TechStore registrados desde configuración centralizada en infra/config-repo.

    1.4 Motivacion de la sesión

    Cuando un sistema crece, los servicios ya no deben depender de puertos fijos en el host. Un microservicio puede tener varias instancias, reiniciarse o cambiar de ubicación. El reto es que los demás componentes lo encuentren sin conocer su host y puerto exactos.

    Preguntas para los estudiantes:

    1. ¿Qué problema aparece cuando cada servicio tiene un puerto fijo?

      Respuesta (TechStore): Solo puede correr una instancia por máquina; si el puerto está ocupado el servicio no arranca. Gateway y otros clientes deben conocer IP:puerto manualmente y actualizarlo en cada reinicio o escalado (por ejemplo, recordar que producto está en 9091 y catalogo en 9081).

    2. ¿Cómo se ubica un servicio si existen varias instancias?

      Respuesta (TechStore): Cada instancia se registra en registry-server (http://localhost:7081) con el mismo nombre lógico (CATALOGO, PRODUCTO, AUTH, etc.) y puerto distinto. El cliente consulta Eureka y obtiene la lista de instancias vivas; en S04 el Gateway hará eso automáticamente.

    3. ¿Qué evidencia demuestra que un servicio está registrado dinámicamente?

      Respuesta (TechStore): Dashboard en http://localhost:7081 mostrando el servicio con estado UP; logs con Registered instance o heartbeat; y curl http://localhost:7081/eureka/apps/CATALOGO devolviendo una o más instancias con host y puerto actualizados.

    1.5 Ubicación en el curso

    • Unidad: U1 - Sistema distribuido base orientado a producción.
    • Producto de unidad: sistema distribuido base funcional, configurable y preparado para múltiples instancias.
    • Avance del producto en esta sesión: registro dinamico de servicios y ejecución concurrente.

    2. Explica

    Tiempo: 15 min.

    2.1 Conceptos clave

    • Registro de servicios: componente donde los microservicios anuncian su existencia.
    • Descubrimiento de servicios: capacidad de encontrar instancias por nombre lógico.
    • Puerto dinamico: puerto asignado automáticamente para permitir múltiples instancias.
    • Heartbeat: señal periódica que indica que una instancia sigue viva.

    2.3 Observabilidad y diagnóstico

    Señales a revisar:

    • Health de Config Server.
    • Health y dashboard de Eureka.
    • Logs de registro de clientes.
    • Instancias con nombres lógicos (CATALOGO, PRODUCTO, AUTH, etc.).
    • Puertos dinámicos distintos para un mismo servicio.

    Errores frecuentes:

    Problema Causa probable Solución
    Servicio no aparece en Eureka Eureka apagado o URL incorrecta Revisar Config Server y eureka.client.service-url
    Solo aparece una instancia No se levanto una segunda terminal Ejecutar otra instancia con mvn spring-boot:run -Dspring-boot.run.arguments=--server.port=0
    Nombre incorrecto spring.application.name mal definido Revisar archivo {servicio}-dev.yml y defaultZone: http://localhost:7081/eureka

    3.1 Crear la base de infraestructura para Eureka

    Producto del paso: proyecto Eureka Server creado dentro de infra/registry-server.

    En el monorepo ProyectoMS2026 (TechStore), Eureka vive en:

    infra/registry-server

    Si partes desde cero, crea la carpeta dentro de infra y genera el proyecto Spring Boot desde VS Code.

    3.2 Crear proyecto Eureka Server desde VS Code

    Producto del paso: proyecto Spring Boot registry-server creado dentro de infra/registry-server.

    Configuración sugerida en Spring Initializr:

    Campo Valor
    Project Maven Project
    Spring Boot 3.5.x
    Language Java
    Java 17
    Group Id com.upeu
    Artifact Id registry-server
    Package name com.upeu.registryserver
    Packaging Jar
    Ubicación infra/registry-server

    Dependencias:

    Grupo Dependencias Propósito
    Spring Cloud Eureka Server Registro y descubrimiento de servicios
    Spring Cloud Config Client Leer configuración desde Config Server
    Operación Spring Boot Actuator Health y diagnóstico
    Productividad Spring Boot DevTools Facilitar ejecución en desarrollo

    3.3 Habilitar Eureka Server

    Agregar @EnableEurekaServer en la clase principal del proyecto.

    package com.upeu.registryserver;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.cloud.netflix.eureka.server.EnableEurekaServer;

@SpringBootApplication
@EnableEurekaServer
public class RegistryServerApplication {
    public static void main(String[] args) {
        SpringApplication.run(RegistryServerApplication.class, args);
    }
}

    3.4 Configurar application.yml base de Eureka

    Producto del paso: Eureka preparado para leer configuración externa.

    En infra/registry-server/src/main/resources/application.yml:

    server:
  port: 7081

spring:
  application:
    name: registry-server
  profiles:
    active: dev
  config:
    import: "optional:configserver:${CONFIG_SERVER_URL:http://localhost:7071}"

    3.5 Crear configuración de Eureka en config-repo

    Crea el archivo DEV:

    infra/config-repo/registry-server-dev.yml

    Pega este contenido:

    spring:
  application:
    name: registry-server

eureka:
  client:
    register-with-eureka: false
    fetch-registry: false

management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics
  endpoint:
    health:
      show-details: always

    Crea el archivo PROD:

    infra/config-repo/registry-server-prod.yml

    Pega este contenido:

    spring:
  application:
    name: registry-server

  client:
    register-with-eureka: false
    fetch-registry: false

  endpoints:
    web:
      exposure:
        include: health,info,metrics

    health:
      show-details: never

    3.6 Probar configuración de Eureka desde Config Server

    Con Config Server ejecutando:

    PowerShell:

    Invoke-RestMethod -Method Get -Uri "http://localhost:7071/registry-server/dev"
Invoke-RestMethod -Method Get -Uri "http://localhost:7071/registry-server/prod"

    bash macOS/Linux:

    curl http://localhost:7071/registry-server/dev
curl http://localhost:7071/registry-server/prod

    Resultado esperado:

    • La respuesta indica name: registry-server.
    • El perfil consultado aparece como dev o prod.
    • En propertySources aparece registry-server-dev.yml o registry-server-prod.yml.

    3.8 Agregar Eureka Client a microservicios

    Producto del paso: los seis microservicios TechStore preparados para registrarse en Eureka.

    Repite en services/catalogo, services/producto, services/auth, services/pedido, services/pago y services/carrito. En el pom.xml de cada uno agrega la dependencia:

    <dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-netflix-eureka-client</artifactId>
</dependency>

    Si el microservicio aún no tiene Spring Cloud, agrega también la versión:

    <properties>
    <java.version>17</java.version>
    <spring-cloud.version>2025.0.2</spring-cloud.version>
</properties>

    Y el BOM:

    <dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.cloud</groupId>
            <artifactId>spring-cloud-dependencies</artifactId>
            <version>${spring-cloud.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

    El nombre del servicio debe coincidir con el archivo de Config Server y con lo que se vera en Eureka:

    spring:
  application:
    name: catalogo

    3.9 Configurar clientes Eureka desde Config Server

    Producto del paso: microservicios conectados a Eureka desde configuración externa.

    En cada archivo {servicio}-dev.yml de infra/config-repo (por ejemplo catalogo-dev.yml, producto-dev.yml, auth-dev.yml, etc.), agrega o verifica:

    eureka:
  instance:
    hostname: localhost
    prefer-ip-address: false
    instance-id: ${spring.application.name}:${local.server.port:${random.value}}
    metadata-map:
      instance-port: ${local.server.port:${server.port}}
  client:
    service-url:
      defaultZone: http://localhost:7081/eureka

    En cada archivo {servicio}-prod.yml, agrega o verifica:

    eureka:
  client:
    service-url:
      defaultZone: http://registry-server:7081/eureka

    3.10 Levantar catalogo en DEV y verificar registro

    PowerShell / bash macOS/Linux:

    cd services/catalogo
docker compose -f docker-compose-dev.yml up -d
mvn spring-boot:run

    Resultado esperado:

    • catalogo arranca en el puerto fijo 9081 definido en catalogo-dev.yml.
    • En logs aparece registro hacia Eureka.
    • En http://localhost:7081 aparece CATALOGO con una instancia en 9081.

    3.11 Levantar una segunda instancia en DEV

    La primera instancia ya ocupa 9081. Para demostrar escalado horizontal, levanta una segunda instancia con puerto dinámico (0 = Spring asigna un puerto libre):

    PowerShell / bash macOS/Linux:

    cd services/catalogo
mvn spring-boot:run -Dspring-boot.run.arguments=--server.port=0

    En PowerShell también puedes usar:

    mvn spring-boot:run "-Dspring-boot.run.arguments=--server.port=0"

    3.12 Verificar múltiples instancias

    Abre:

    http://localhost:7081

    Resultado esperado:

    • Eureka muestra CATALOGO con dos instancias (puertos 9081 y otro asignado dinámicamente).
    • Puedes confirmar con curl http://localhost:7081/eureka/apps/CATALOGO.

    3.14 Respetar el orden de arranque en PROD local

    En PROD local, primero se levanta infraestructura y luego microservicios:

    1. infra -> config-server + registry-server
2. services/catalogo -> BD + catalogo
3. services/producto -> BD + producto
4. services/auth, pedido, pago, carrito -> mismo patrón

    La red compartida es creada por infra/docker-compose.yml.

    3.15 Probar registro en PROD local

    Producto del paso: Eureka ejecutando en Docker y microservicios registrados dentro de la red ms-net.

    Primero levanta infraestructura:

    PowerShell / bash macOS/Linux:

    cd infra
docker compose up -d --build config-server registry-server
docker compose ps

    Verifica desde el host con PowerShell:

    Invoke-RestMethod -Method Get -Uri "http://localhost:7072/registry-server/prod"
Invoke-RestMethod -Method Get -Uri "http://localhost:7082/actuator/health"

    Verifica desde el host con bash macOS/Linux:

    curl http://localhost:7072/registry-server/prod
curl http://localhost:7082/actuator/health

    Pregunta: ¿Por qué el descubrimiento de servicios es necesario antes de usar Gateway y balanceo de carga?

    Respuesta de referencia (Equipo 07 — TechStore-g2):

    Gateway y un balanceador necesitan saber qué instancias de cada microservicio están vivas y en qué host:puerto escuchan. Sin Eureka, habría que configurar manualmente cada ruta y actualizarla en cada reinicio o escalado. Con registry-server, producto, catalogo y el resto se anuncian por nombre lógico; Gateway (S04) consultará esa lista y repartirá peticiones entre instancias sin hardcodear puertos. Es el paso previo para que el sistema escale horizontalmente de forma automática.

    5.3 Preguntas de defensa y reflexión

    1. ¿Por qué un microservicio usa puerto dinámico?

      Respuesta (TechStore): Permite levantar varias instancias del mismo servicio en la misma máquina sin conflicto de puertos. En TechStore, la primera instancia de catalogo usa 9081 fijo; la segunda usa --server.port=0 para que Spring elija un puerto libre. En PROD Docker, el escalado con --scale catalogo=2 también evita colisiones.

    2. ¿Qué ventaja tiene registrar por nombre lógico?

      Respuesta (TechStore): Los clientes (Gateway en S04, otros MS) piden PRODUCTO o CATALOGO a Eureka sin conocer IP ni puerto. Si una instancia cae o se agrega otra, solo cambia la lista en el registry; no hay que editar configuración en cada consumidor.

    3. ¿Cómo demuestras que hay dos instancias?

      Respuesta (TechStore): Captura del dashboard en http://localhost:7081 mostrando el mismo servicio dos veces; o curl http://localhost:7081/eureka/apps/CATALOGO (o PRODUCTO) con dos nodos <instance> y puertos distintos; o logs con dos líneas Registered instance.

    4. ¿Qué pasa si Eureka no está disponible al arrancar?

      Respuesta (TechStore): El microservicio suele arrancar igual (la app funciona), pero no se registra ni renueva heartbeat. Aparecerá en logs un error de conexión a defaultZone. Al levantar registry-server después, el cliente reintenta y se registra. Hasta entonces, ningún consumidor que dependa de descubrimiento lo encontrará.

    5. ¿Qué diferencia hay entre Config Server y Eureka?

      Respuesta (TechStore): Config Server (7071/7072) entrega configuración estática o por perfil (puertos, JDBC, flags) desde infra/config-repo. Eureka (registry-server, 7081/7082) mantiene un directorio vivo de instancias en ejecución: quién está UP, en qué host:puerto y con qué heartbeat. Uno configura el comportamiento al arrancar; el otro refleja el estado runtime del clúster.
