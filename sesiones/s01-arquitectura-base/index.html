    S1 - Construcción de un servicio base para un sistema distribuido

    1. Introducción

    Tiempo: 20 min.

    1.1 Propósito

    Construir el primer servicio de negocio del sistema y dejarlo preparado para crecer hacia una arquitectura distribuida.

    1.2 Resultado de aprendizaje

    El estudiante implementa un microservicio stateless con API REST, persistencia, validación, documentación de endpoints, health check y ejecución reproducible en desarrollo y producción.

    1.3 Producto de sesión

    catalogo funcional con CRUD de categorías, MySQL en Docker, Swagger, Actuator, README operativo y pruebas por shell. En DEV el servicio corre en el puerto 9081 y la base de datos en 3381.

    1.4 Motivacion de la sesión

    1.4.1 Caso: TechStore — plataforma de comercio electrónico

    TechStore es una tienda en línea de productos tecnológicos. Inicialmente, todo el sistema (catálogo, productos, carrito, pedidos, pagos con Mercado Pago y autenticación) fue construido como una sola aplicación monolítica.

    Con el crecimiento del negocio comienzan a aparecer problemas:

    • El sistema tarda más en desplegarse.
    • Errores en un módulo afectan a todo el sistema.
    • Es difícil escalar partes específicas del sistema.
    • Los equipos de desarrollo trabajan sobre el mismo código.

    El equipo de ingeniería decide rediseñar la arquitectura del sistema utilizando microservicios dentro del monorepo TechStore-Proyecto.

    Preguntas para los estudiantes:

    1. ¿Qué problemas tiene la arquitectura monolítica en este caso?
    2. ¿Por qué una empresa migraría a microservicios?
    3. ¿Qué ventajas ofrece dividir el sistema en servicios?

    1.4.2 Respuestas orientativas

    1. ¿Qué problemas tiene la arquitectura monolítica en TechStore?

    • Cada cambio pequeño (por ejemplo, en pagos) obliga a redesplegar toda la aplicación.
    • Si falla el módulo de Mercado Pago, también puede caer el catálogo o el login.
    • En campañas o fechas pico no se puede escalar solo el módulo de productos o pedidos.
    • Varios equipos modifican el mismo código y los conflictos de integración se vuelven frecuentes.

    2. ¿Por qué una empresa migraría a microservicios?

    • Para que cada dominio de negocio evolucione y se despliegue de forma independiente (catálogo, producto, pedido, pago, auth, carrito).
    • Para reducir el impacto de un fallo: un error en pago no debería tumbar catalogo.
    • Para escalar solo lo que más tráfico recibe (por ejemplo, producto en temporada alta).
    • Para alinear equipos con servicios concretos y entregar valor más rápido.

    3. ¿Qué ventajas ofrece dividir el sistema en servicios?

    • Responsabilidad clara: catalogo solo gestiona categorías; producto solo productos; pedido solo pedidos.
    • Base de datos propia por servicio (db_catalogo, db_producto, etc.).
    • Infraestructura compartida: Config Server (7071), Eureka (7081) y Gateway (7091).
    • Comunicación asíncrona con Kafka entre pedidos y pagos.
    • Frontend desacoplado: techstore-proyecto (Angular) consume todo por el Gateway.

    En esta sesión se inicia ese rediseño construyendo el primer componente de TechStore: el microservicio catalogo en services/catalogo.

    1.5 Ubicación en el curso

    • Proyecto: TechStore-Proyecto (monorepo ProyectoMS2026).
    • Unidad: U1 — Sistema distribuido base orientado a producción.
    • Producto de unidad: sistema distribuido funcional, configurable y preparado para múltiples instancias, ejecutable en desarrollo y producción local en paralelo.
    • Avance en S1: primer microservicio REST (services/catalogo), persistente con MySQL, observable con Actuator y ejecutable fuera del IDE.
    • Documentación: sitio publicado en techstore-gh-pages; frontend Angular en techstore-proyecto (integración en S11).

    2. Explica

    Tiempo: 15 min.

    2.1 Conceptos clave

    Un microservicio debe tener responsabilidad clara, persistencia propia, configuración por ambiente y capacidad de ejecutarse de forma independiente.

    Ejemplo: catalogo se encarga de gestionar categorías y su propia base de datos db_catalogo. No debería guardar productos, pedidos ni pagos. Si más adelante producto necesita saber a qué categoría pertenece un artículo, consulta a catalogo por red en lugar de leer directamente su base de datos.

    2.2 Arquitectura del producto en TechStore

    Cada microservicio de TechStore repite el mismo patrón de despliegue: en DEV la aplicación Spring Boot corre con Maven en el host y MySQL corre en Docker; en PROD local aplicación y MySQL van en contenedores conectados a la red ms-net.

    2.2.1 Regla práctica general

    • DEV: mvn spring-boot:run en el host + docker compose -f services/producto/docker-compose-dev.yml up -d para MySQL.
    • PROD local: docker compose up -d levanta app (jar) y MySQL en la red interna del servicio (*-int) más ms-net.
    • Host vs contenedor: fuera de Docker usa localhost:<puerto-publicado>; dentro de Docker usa mysql-<servicio>:3306.
    • S1: solo construyes catalogo; los demás diagramas son referencia del monorepo.

    3.3.6 Revisar logs y trazabilidad interna

    Revisa filter/CorrelationIdFilter.java. Este filtro agrega un identificador de trazabilidad a cada request usando el header X-Trace-ID. Si el cliente no lo envia, el filtro genera un UUID.

    En S1 la trazabilidad es interna al microservicio:

    Cliente shell / Swagger -> Controller -> Service -> Repository -> BD

    Todos los logs producidos durante esa petición pueden compartir el mismo traceId.

    Revisa también src/main/resources/logback-spring.xml. Este archivo define el formato de logs e incluye el traceId en cada línea:

    [%X{traceId}]

    También configura salida por consola y archivo en:

    logs/catalogo.log

    Más adelante, cuando se agreguen Gateway, Feign o frontend, el mismo header X-Trace-ID podrá propagarse entre componentes para trazabilidad distribuida.

    5.3 Preguntas de defensa y reflexión

    1. ¿Por qué separar el sistema en microservicios?

      Respuesta (TechStore): Cada dominio (catálogo, producto, pedido, pago, carrito, auth) evoluciona y despliega de forma independiente. Un fallo o cambio en pago no obliga a recompilar todo el monorepo ProyectoMS2026.

    2. ¿Qué ventaja tiene Docker en desarrollo?

      Respuesta (TechStore): MySQL por servicio en puertos fijos (3381, 3391, etc.) sin instalar seis BDs en el host; la red ms-net unifica infra en PROD local.

    3. ¿Cómo se nombra un microservicio en TechStore?

      Respuesta (TechStore): Carpeta y artifactId = nombre del servicio (catalogo, no catalogo); coincide con spring.application.name y archivos en config-repo.
