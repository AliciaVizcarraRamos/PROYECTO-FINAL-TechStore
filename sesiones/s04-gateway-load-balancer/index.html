    S4 - Punto único de acceso y distribución de tráfico

    1. Introducción

    Tiempo: 20 min.

    1.1 Propósito

    Incorporar un punto único de acceso para que los clientes consuman el sistema mediante Gateway y para distribuir tráfico entre instancias disponibles.

    1.2 Resultado de aprendizaje

    El estudiante configura rutas en Gateway, consume microservicios mediante un acceso centralizado y evidencia balanceo de carga.

    1.3 Producto de sesión

    Gateway operativo en infra/gateway (puerto DEV 7091, PROD 7092), con rutas hacia los seis microservicios TechStore registrados en Eureka y pruebas de distribución de tráfico.

    1.4 Motivación de la sesión

    Si un cliente conoce directamente todos los microservicios, queda acoplado a sus puertos, rutas y ubicaciones. Un Gateway permite centralizar el acceso y esconder la topología interna del sistema.

    Preguntas para los estudiantes:

    1. ¿Por qué el cliente no debería conocer todos los microservicios?

      Respuesta (TechStore): Porque tendría que recordar seis puertos distintos (9081, 9091, 8041, etc.), actualizarlos al escalar y exponer la topología interna. Con Gateway en 7091 el cliente solo usa un host y rutas como /api/v1/productos.

    2. ¿Qué problema aparece si cada cliente llama directamente a cada microservicio?

      Respuesta (TechStore): Acoplamiento fuerte, duplicación de URLs en frontend y scripts, imposibilidad de balancear sin lógica en cada cliente, y cambios costosos cuando un servicio cambia de puerto o se agregan instancias.

    3. ¿Cómo se demuestra que existe balanceo de carga?

      Respuesta (TechStore): Levantar dos instancias de catalogo en Eureka y llamar varias veces a http://localhost:7091/api/v1/catalogo/instancia; las respuestas alternan el campo instancia (puerto distinto). También sirve capturar logs del Gateway con destinos diferentes.

    1.5 Ubicación en el curso

    • Unidad: U1 - Sistema distribuido base orientado a producción.
    • Producto de unidad: sistema distribuido base funcional, configurable y preparado para múltiples instancias.
    • Avance del producto en esta sesión: acceso centralizado con rutas y balanceo de carga.

    2. Explica

    Tiempo: 15 min.

    2.1 Conceptos clave

    • Gateway: punto único de entrada al sistema.
    • Ruta: regla que dirige una petición hacia un servicio.
    • Load Balancer: selecciona una instancia disponible del servicio.
    • lb://: esquema usado para resolver servicios registrados por nombre lógico.

    2.3 Observabilidad y diagnóstico

    Señales a revisar:

    • Health de Gateway.
    • Eureka con servicios registrados.
    • Logs de rutas.
    • Respuestas repetidas desde instancias distintas.

    Errores frecuentes:

    Problema Causa probable Solución
    503 Servicio no registrado o Eureka no disponible Revisar Eureka y registros
    404 Ruta mal configurada Revisar predicates y paths
    No balancea Solo existe una instancia Levantar otra instancia con mvn spring-boot:run -Dspring-boot.run.arguments=--server.port=0

    3.14 Evidenciar balanceo

    Producto del paso: se observa distribución de tráfico entre instancias disponibles.

    El endpoint de instancia debe existir en catalogo. Si todavía no lo tienes, crea este controlador:

    services/catalogo/src/main/java/com/upeu/catalogo/controller/GatewayInstanciasController.java

    Pega este código:

    package com.upeu.catalogo.controller;

import java.net.InetAddress;
import java.net.UnknownHostException;
import java.util.Map;

import org.springframework.core.env.Environment;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

import lombok.RequiredArgsConstructor;

@RestController
@RequestMapping("/api/v1/catalogo")
@RequiredArgsConstructor
public class GatewayInstanciasController {

    private final Environment environment;

    @GetMapping("/instancia")
    public Map<String, String> instancia() {
        return Map.of(
                "servicio", "catalogo",
                "instancia", environment.getProperty("local.server.port", "N/A"),
                "serverPort", environment.getProperty("server.port", "N/A"),
                "host", hostName());
    }

    private String hostName() {
        try {
            return InetAddress.getLocalHost().getHostName();
        } catch (UnknownHostException e) {
            return "unknown";
        }
    }
}

    Ejecuta varias veces por Gateway:

    PowerShell:

    1..10 | ForEach-Object {
  Invoke-RestMethod -Method Get -Uri "http://localhost:7091/api/v1/catalogo/instancia"
}

    bash macOS/Linux:

    for i in {1..10}; do
  curl http://localhost:7091/api/v1/catalogo/instancia
  echo
done

    Resultado esperado:

    • Gateway responde.
    • Eureka muestra instancias disponibles.
    • Las respuestas repetidas alternan entre instancias o muestran puertos distintos.

    3.14.1 Probar otros microservicios por Gateway

    Repite la misma idea con cualquier servicio de la tabla 3.5.1. Ejemplo con producto (autónomo Equipo 07):

    3.15 Probar error esperado

    Producto del paso: estudiante diferencia una falla de ruta y una falla de disponibilidad.

    5.3 Preguntas de defensa y reflexión

    1. ¿Por qué el cliente debe entrar por Gateway?

      Respuesta (TechStore): Un solo punto de entrada (7091/7092), rutas estables (/api/v1/productos) y sin exponer los seis puertos internos. Facilita CORS, seguridad (S07) y cambios de topología sin tocar el cliente.

    2. ¿Qué significa lb://?

      Respuesta (TechStore): Esquema de Spring Cloud Gateway que resuelve el host mediante Eureka. lb://producto consulta instancias registradas de producto y el load balancer elige una (round-robin por defecto).

    3. ¿Cómo se relacionan Gateway y Eureka?

      Respuesta (TechStore): Los microservicios se registran en registry-server (7081). Gateway es cliente Eureka y usa esa lista para enrutar lb://*. Sin Eureka, Gateway no sabría a qué IP:puerto enviar cada petición.

    4. ¿Cómo diagnosticas un 503?

      Respuesta (TechStore): Verificar que el servicio aparece UP en http://localhost:7081, que la ruta usa el nombre correcto (lb://catalogo, no lb://catalogo), que hay al menos una instancia y que Eureka está activo antes que Gateway y los MS.

    5. ¿Cómo evidencias balanceo?

      Respuesta (TechStore): Dos instancias del mismo MS en Eureka; llamar repetidamente /api/v1/catalogo/instancia o /api/v1/producto/instancia por Gateway y mostrar que el campo instancia (puerto) cambia entre respuestas.
